# Myon Virtual Machine（MVM）バイトコード仕様書 v0.1

## 0. 概要

本書は **Myon Virtual Machine（以下 MVM）** の設計仕様を定める。MVM は、
これまでの「AST をそのまま辿って評価するツリーウォーク型インタプリタ」
（`src/interpreter.c`）に加えて新設する、**バイトコード実行エンジン**である。

- `.myon` ファイル … 従来通りツリーウォーク実行（**本仕様では一切変更しない**）
- `.myc` ファイル … AST からコンパイルされた MVM バイトコードを VM が直接実行（**新設**）

高速化のねらいは、木構造の再帰的なノード走査・型ディスパッチ・環境（`Env`）の
親チェーン探索といった、ツリーウォーク特有の実行時オーバーヘッドを、
**コンパイル時に静的に解決してしまう**ことにある。具体的には次の 3 点である。

| 削減対象 | ツリーウォーク版 | MVM 版 |
|---|---|---|
| ノード走査 | 毎回 `Expr`/`Stmt` を再帰的に辿る | 平坦なバイトコード列を線形に読む |
| 変数解決 | 実行時に `Env` の親を辿る（9章） | コンパイル時にスロット番号へ解決 |
| 分岐 | C の再帰呼び出しで制御構文を表現 | 単純なジャンプ命令 |

### 0.1 本書の位置付けとスコープ

- 本ステップ（Step4）では **コンパイラ本体（Step5）も VM 本体（Step6）も実装しない**。
  本書は、それらを実装するための **設計図**（命令セット・`.myc` フォーマット・
  値表現・スタック設計・静的スコープ解決アルゴリズム）を確定させることが目的である。
- 本書は既存の `docs/myon_spec.md`（言語仕様書 v0.1）に準拠する。用語・章立て・
  表とコード例のスタイルを踏襲し、日本語で記述する。
- 本書内で「§N.M」と書いた場合は本書の節を、「言語仕様 §N.M」と書いた場合は
  `docs/myon_spec.md` の節を指す。

### 0.2 設計方針まとめ

| 項目 | 方針 | 根拠 |
|---|---|---|
| マシン方式 | **スタックマシン** | ツリーウォーク評価と対応づけが自然（§1.1） |
| 命令長 | **可変長**（1 バイトのオペコード＋固定幅オペランド） | 命令セットの単純さと実装容易性（§1.2） |
| 値表現 | **既存 `Value`/`Obj` を流用（方針A）** | 実装コスト最小・まず効果を出す（§2） |
| 定数プール | コード本体から分離して保持 | リテラルの重複排除・シリアライズ容易化（§1.3） |
| 変数解決 | **コンパイル時に静的スロット割当** | 実行時の `Env` 探索を排除（§5） |
| 組み込み関数 | 個別命令化せず **ネイティブ呼び出し 1 命令**で関数テーブルを引く | 命令セット肥大化の防止（§4.13） |
| 非対応機能 | async/net/ffi は **明示エラー**（フォールバックしない） | 利用者の混乱防止（§7） |
| エンディアン | **リトルエンディアン固定**でシリアライズ | 単純化。ヘッダに識別子も持つ（§6） |

## 1. 全体アーキテクチャ

### 1.1 スタックマシンの採用

MVM は **スタックマシン**として設計する。

**理由**：既存のツリーウォーク評価器は「式（`Expr`）を評価するとちょうど 1 つの
`Value` が得られる」という一貫したモデルを持つ（`src/interpreter.c` の
`eval_expr()` が `Value` を返す構造）。スタックマシンは「式を評価して結果を
オペランドスタックに push する」というモデルであり、両者は素直に対応づく。

```
式ツリー                     バイトコード（スタックマシン）
    +                        PUSH_CONST 1      ; スタック: [1]
   / \          ==>          PUSH_CONST 2      ; スタック: [1, 2]
  1   2                      ADD               ; スタック: [3]
```

この対応の自然さにより、Step5 のコンパイラは AST を後順（post-order）で走査して
オペランドを先に、演算命令を後に並べるだけでコード生成でき、実装リスクが小さい。

**レジスタマシンを採らない理由**：レジスタマシンは命令数を減らせて理論上は高速だが、
レジスタ割当（線形走査やグラフ彩色）というコンパイラ側の実装負荷が大きく、本ステップの
「まずバイトコード化の効果を最短で出す」という優先順位に合わない。レジスタ化は
将来の最適化課題として §10（Open Questions）に記録する。

### 1.2 命令フォーマット（可変長）

命令は **可変長**とする。先頭 1 バイトがオペコード、続いてオペコードごとに定まる
固定幅のオペランドが 0〜複数個続く。

```
 バイト:  [ opcode(1) ][ operand ... ]
```

- オペコードは `uint8_t`（0〜255）。将来の拡張のため 256 個の枠を確保する。
- オペランドは以下の固定幅のいずれか。すべて**リトルエンディアン**で格納する。

| オペランド種別 | 幅 | 用途 |
|---|---|---|
| `u8`  | 1 バイト | 引数個数、ネイティブ関数の小さいID など |
| `u16` | 2 バイト | 定数プール索引、ローカルスロット番号、ジャンプ先の相対オフセット |
| `u32` | 4 バイト | （予約）大きな索引が必要になった場合の拡張用 |

- ジャンプ先は **符号付き 16 ビットの相対オフセット**（`s16`）で表現する。
  基準は「そのジャンプ命令のオペランド直後のアドレス」とする（§4.7）。
- 命令はバイト境界に詰めて並べる（アラインメントのためのパディングは行わない）。
  可変長のため、逆アセンブラ／VM は必ずオペコードから読み進める。

**固定長にしない理由**：オペコードごとにオペランド構成が異なるため、固定長にすると
未使用バイトのパディングが増えてコードサイズが膨らむ。Myon の当面の目的は「命令
セットの単純さと実装の確実性」であり、可変長でも実行時のデコードコストは十分小さい。

### 1.3 定数プール

文字列リテラル・浮動小数点定数など、コード本体（命令列）に直接埋め込みにくい値は、
**チャンクごとの定数プール**に格納し、命令からは `u16` の索引で参照する。

- 定数プールは `Value` の配列と概念的に等価だが、`.myc` 上では §6.3 のシリアライズ
  形式で保存する。int も含めてすべての即値をここに置く方針とする（`PUSH_CONST`
  命令はプール索引だけを持つ）。
- 同一のリテラルは **コンパイル時に重複排除**してよい（同じ値は同じ索引を共有）。
- 定数プールに置けるのは、以下の「静的に確定するリテラル」のみとする。
  配列・マップ・構造体などの複合値は実行時に構築する（定数プールには入れない）。

| 定数種別 | 対応する AST | `Value` 表現 |
|---|---|---|
| int | `EXPR_INT_LIT` | `value_int` |
| float | `EXPR_FLOAT_LIT` | `value_float` |
| bool | `EXPR_BOOL_LIT` | `value_bool` |
| str | `EXPR_STRING`（補間なしの純粋な文字列） | `value_str` |
| nil | `EXPR_NIL` | `value_nil` |

> **補足**：bool と nil は種類が 2〜3 通りしかないため、専用命令
> `PUSH_TRUE` / `PUSH_FALSE` / `PUSH_NIL` を用意し、定数プールを消費しない設計とする
> （§4.1）。int/float/str のみプールを使う。

### 1.4 実行モデルとチャンク

MVM の実行単位を **チャンク（Chunk）** と呼ぶ。1 つのチャンクは次を持つ。

```
Chunk {
    code[]        : バイトコード列（命令の並び）
    constants[]   : 定数プール（この関数が参照するリテラル）
    num_locals    : このチャンクが使うローカルスロット総数（コンパイル時に確定）
    num_params    : 引数の個数
    name          : 診断用の関数名（トップレベルは "<main>"）
    lines[]       : （任意）命令→ソース行の対応表。実行時エラーの行表示用
}
```

- トップレベルのプログラム全体が 1 つの「main チャンク」になる。
- 各 `myon.func` / `myon.lambda` / 構造体メソッドは、それぞれ独立したチャンクに
  コンパイルされる（§4.8）。
- `.myc` ファイルは「複数チャンクの集合＋メタ情報」をシリアライズしたものである（§6）。

## 2. 値表現

本仕様では **方針 A：既存の `Value`/`Obj`（`src/value.h`）をそのまま MVM の値表現として
流用する**ことを採用する。

### 2.1 採用理由

- 実装コストが最小。`value_copy` / `value_free`（参照カウント）・`value_truthy` ・
  `value_equal` ・`value_to_cstr` など、ツリーウォーク版が積み上げてきたランタイム
  ヘルパをそのまま再利用できる。
- ネイティブ関数（`myon.math` 等）は既に `Value` を引数・戻り値とする形で実装されて
  いるため、MVM から呼ぶときに **値の変換が不要**になる（§4.13）。
- 本ステップの目的は「バイトコード化による分岐予測改善・関数呼び出しオーバーヘッド
  削減の効果を最短で出す」ことであり、値表現そのものの刷新は目的から外れる。

### 2.2 方針 A のオーバーヘッドと割り切り

方針 A は、`Obj` の malloc/free と参照カウント操作というツリーウォーク版と同じ
コストを引き継ぐ。したがって str/array/map/struct を多用するコードでは高速化幅が
限定的になり得る。しかし **制御構文・関数呼び出し・算術演算が中心のコード**では、
ノード走査と変数解決の削減効果が支配的になり、十分な高速化が見込める。

値表現の刷新（**方針 B**：タグ付きユニオンの平坦化や NaN-boxing）は、真の高速化に
有効だが実装コストが高いため、**本スコープには含めず** §10（Open Questions）に将来
課題として記録する。

### 2.3 オペランドスタック上の値

- オペランドスタックの各スロットは 1 つの `Value` を保持する（`Value` は
  `{ Type type; union { i / f / b / obj } }` の値型）。
- スタックへ push するときは、リテラルなら定数プールの `Value` を `value_copy` して
  積む（`Obj` は参照カウントを増やして共有）。
- pop して破棄するときは `value_free` で 1 参照を落とす。
- 演算命令は、オペランドを pop → C 側で計算 → 結果を push、の順で処理し、
  途中で pop した中間値は責任を持って `value_free` する（メモリリーク防止）。

### 2.4 nil / void の扱い

- `myon.nil`（`TYPE_NIL`）は言語仕様 §2.4 の通り「エラー値専用のセンチネル」であり、
  MVM でも同じ意味論を維持する。`PUSH_NIL` 命令で積む。
- `void`（`TYPE_VOID`）は「値を返さない関数の戻り」を表す内部値であり、`ret` を伴わない
  関数の暗黙戻り（§4.8）で用いる。

## 3. スタックとコールフレーム設計

### 3.1 2 つのスタック

MVM は次の 2 本のスタックを持つ。

1. **オペランドスタック（value stack）**：式評価の途中結果を積む `Value` の LIFO。
2. **コールスタック（frame stack）**：関数呼び出しのコールフレームを積む。

### 3.2 コールフレーム（CallFrame）

1 回の関数呼び出しにつき 1 つのコールフレームを持つ。

```
CallFrame {
    chunk    : 実行中のチャンクへの参照
    ip       : インストラクションポインタ（chunk->code 内の現在位置）
    base     : このフレームのローカル領域が始まる、オペランドスタック上の底位置
    ret_count: 呼び出し側が期待する戻り値の個数（複数戻り値対応、§4.9）
}
```

### 3.3 ローカル変数のスタック配置

ローカル変数は **オペランドスタックの底に連続配置する**（いわゆる「レジスタウィンドウ」
的な配置）。フレームの `base` を基準に、`slot` 番号でアクセスする。

```
オペランドスタック（上に伸びる）
  ...                    ← 式評価の一時領域（top 側）
  [base+2] local #2
  [base+1] local #1
  [base+0] local #0（= 第1引数 or 最初のローカル）
  ← base（このフレームのローカル領域の底）
  （呼び出し側フレームの領域）
```

- 関数に入るとき、引数はすでに呼び出し側が push 済みで、それが `slot 0..num_params-1`
  になる（§4.8 の呼び出し規約）。
- `LOAD_LOCAL slot` は `stack[base + slot]` を `value_copy` して top に積む。
- `STORE_LOCAL slot` は top を pop して `stack[base + slot]` に格納する
  （既存値は `value_free` してから上書き）。
- `num_locals`（チャンクが使うスロット総数）はコンパイル時に確定するため、関数入口で
  ローカル領域をまとめて確保できる（§5）。

### 3.4 スタックオーバーフロー

コールスタックには上限（例：初期実装で 1024 フレーム）を設け、超過時は
「stack overflow（再帰が深すぎます）」という実行時エラーを出す。これは言語仕様
§6.2.1 の診断形式に合わせる（§8）。

## 4. 命令セット（オペコード一覧）

以下に MVM の命令セットを示す。「スタック効果」列は `[ pop → push ]` の形で、命令が
オペランドスタックをどう変化させるかを表す（例：`[a b → c]` は 2 個 pop・1 個 push）。
`ExprKind`/`StmtKind` 列は、対応する AST（`src/ast.h`）を示す。

### 4.0 オペコード番号の割当方針

- `0x00` は `NOP`（デバッグ・パディング用）として予約する。
- 種別ごとに番号帯を分けて将来の追加を容易にする（下表の並びに準拠）。
  実際の数値は Step5/6 実装時に `mvm_opcode.h`（新設予定）で確定するため、本書では
  **ニーモニック（記号名）で規定**し、数値は割当方針のみ示す。

| 帯 | 用途 |
|---|---|
| `0x00`–`0x0F` | スタック・定数ロード |
| `0x10`–`0x2F` | 算術・比較・論理・単項 |
| `0x30`–`0x3F` | ローカル変数 |
| `0x40`–`0x4F` | 分岐・ジャンプ |
| `0x50`–`0x5F` | 関数呼び出し・return |
| `0x60`–`0x6F` | 配列・マップ |
| `0x70`–`0x7F` | 構造体・メンバ・メソッド |
| `0x80`–`0x8F` | 文字列補間・型キャスト |
| `0x90`–`0x9F` | ネイティブ／モジュール呼び出し |

### 4.1 定数ロード

| ニーモニック | オペランド | スタック効果 | 対応 AST | 説明 |
|---|---|---|---|---|
| `NOP` | なし | `[ → ]` | — | 何もしない |
| `PUSH_CONST` | `u16 idx` | `[ → v]` | `EXPR_INT_LIT`/`EXPR_FLOAT_LIT`/`EXPR_STRING`(補間なし) | 定数プール `idx` の値を積む |
| `PUSH_TRUE` | なし | `[ → true]` | `EXPR_BOOL_LIT` | bool `true` を積む |
| `PUSH_FALSE` | なし | `[ → false]` | `EXPR_BOOL_LIT` | bool `false` を積む |
| `PUSH_NIL` | なし | `[ → nil]` | `EXPR_NIL` | `myon.nil` を積む |
| `POP` | なし | `[v → ]` | — | top を捨てる（`value_free`）。式文の結果破棄など |
| `DUP` | なし | `[v → v v]` | — | top を複製（`value_copy`）。複合代入等で使用 |

### 4.2 算術演算（`EXPR_BINARY`）

| ニーモニック | スタック効果 | OpKind | 説明 |
|---|---|---|---|
| `ADD` | `[a b → a+b]` | `OP_ADD` | int/int, float/float。str+str も許可（言語仕様に従う） |
| `SUB` | `[a b → a-b]` | `OP_SUB` | int/float |
| `MUL` | `[a b → a*b]` | `OP_MUL` | int/float |
| `DIV` | `[a b → a/b]` | `OP_DIV` | int/float。ゼロ除算は実行時エラー（§8） |

- 型の厳密性（言語仕様 §2.2）は維持する。`int + float` のような型不一致は
  **実行時エラー**とする。将来コンパイル時に型が確定していれば静的に弾いてよいが、
  初期実装では VM 側で `Value.type` を検査する。
- int の加減乗算は **オーバーフローチェック**を行い、あふれたら実行時エラーとする
  （言語仕様 §0.2・§2.1。ツリーウォーク版 Step12 と同じ挙動）。

### 4.3 比較演算（`EXPR_BINARY`）

| ニーモニック | スタック効果 | OpKind |
|---|---|---|
| `EQ`  | `[a b → a==b]` | `OP_EQ`  |
| `NEQ` | `[a b → a!=b]` | `OP_NEQ` |
| `LT`  | `[a b → a<b]`  | `OP_LT`  |
| `GT`  | `[a b → a>b]`  | `OP_GT`  |
| `LE`  | `[a b → a<=b]` | `OP_LE`  |
| `GE`  | `[a b → a>=b]` | `OP_GE`  |

- `EQ`/`NEQ` は `value_equal`（構造的比較）を用いる。大小比較は int/float/char/str に
  対して言語仕様の規則に従う。結果は必ず bool を積む。

### 4.4 単項演算（`EXPR_UNARY`）

| ニーモニック | スタック効果 | OpKind | 説明 |
|---|---|---|---|
| `NEG` | `[a → -a]` | `OP_NEG` | 数値の符号反転。int オーバーフロー考慮（`-INT64_MIN`） |
| `NOT` | `[a → !a]` | `OP_NOT` | bool 論理否定 |

### 4.5 論理演算（`EXPR_LOGICAL`、短絡評価）

`myon.and` / `myon.or` は **短絡評価**を行う。専用の二項命令は設けず、`JUMP_IF_FALSE` /
`JUMP_IF_TRUE`（§4.7）を使ってコンパイル時に短絡を展開する。

```
# a myon.and b  のコード生成イメージ
        <a を評価>
        JUMP_IF_FALSE Lfalse   ; a が偽なら b を評価せず結果 false
        <b を評価>
        JUMP Lend
Lfalse: PUSH_FALSE
Lend:
```

> 短絡を命令に埋め込まず制御フローで展開する理由：`myon.and`/`myon.or` の意味論
> （右辺を評価しない場合がある）をジャンプで表現するのが最も素直で、副作用のある
> 右辺式にも正しく対応できるため。

### 4.6 ローカル変数

| ニーモニック | オペランド | スタック効果 | 対応 AST | 説明 |
|---|---|---|---|---|
| `LOAD_LOCAL`  | `u16 slot` | `[ → v]` | `EXPR_IDENT`（変数参照） | `stack[base+slot]` を複製して積む |
| `STORE_LOCAL` | `u16 slot` | `[v → ]`  | `STMT_ASSIGN` | top を pop して `stack[base+slot]` に格納 |

- スロット番号 `slot` は **コンパイル時の静的スコープ解決**（§5）で確定する。実行時に
  変数名で `Env` を探索することはしない。
- 多重代入 `a, b = f()`（言語仕様 §9.2）は、`f()` の複数戻り値がスタックに積まれた順に
  対応する `STORE_LOCAL` を並べて実現する（§4.9）。

> **補足（グローバル/クロージャ）**：トップレベル変数も main チャンクのローカルスロット
> として扱う。ネストした関数からの外側変数参照（クロージャ捕捉）は、初期実装では
> **非対応**とし（§7.3 参照）、必要になった時点で `LOAD_UPVALUE`/`CLOSE_UPVALUE` を
> 追加する余地を残す。

### 4.7 分岐・ジャンプ（if/elif/else, while, for, break/continue）

| ニーモニック | オペランド | スタック効果 | 説明 |
|---|---|---|---|
| `JUMP`          | `s16 off` | `[ → ]`  | 無条件に `ip += off` |
| `JUMP_IF_FALSE` | `s16 off` | `[c → ]` | top を pop し、偽なら `ip += off` |
| `JUMP_IF_TRUE`  | `s16 off` | `[c → ]` | top を pop し、真なら `ip += off` |

- オフセット基準は「オペランド直後のアドレス」。前方ジャンプは正、後方（ループ先頭へ
  戻る）は負。コンパイラは前方ジャンプを **バックパッチ**で解決する（ジャンプ先未確定の
  まま命令を出力し、後で off を埋める）。
- `myon.if` / `myon.elif` / `myon.else`（言語仕様 §5.1）は `JUMP_IF_FALSE` と `JUMP` の
  組合せで実現する。
- `myon.while`（§5.2）は「条件評価 → `JUMP_IF_FALSE 脱出` → 本体 → `JUMP 先頭`」。
- `myon.for ... myon.in range(a,b)` は、ループ変数（int）と上限を隠しローカルに置き、
  `LT` と `JUMP_IF_FALSE` で回す。配列反復 `myon.for x myon.in xs` は、隠しインデックスを
  用意し `INDEX_GET`（§4.10）で要素を取り出す形に展開する。
- `myon.break` / `myon.continue` は、コンパイラがループの脱出先／継続先へ `JUMP` を
  生成して表現する（実行時の特別な制御は不要）。ネストしたループでは、対応する
  ループのラベルへバックパッチする。

```
# myon.while cond { body }  のコード生成イメージ
Lstart: <cond を評価>
        JUMP_IF_FALSE Lend
        <body>              ; break → JUMP Lend / continue → JUMP Lstart
        JUMP Lstart
Lend:
```

### 4.8 関数定義とチャンク

各 `myon.func` / `myon.lambda` / メソッドは独立したチャンクにコンパイルする（§1.4）。

- 関数値（`OBJ_FUNC`）は、対応するチャンクの索引を保持する形で構築する。ラムダは
  `MAKE_CLOSURE`（下表）で実行時に関数値を作り積む。
- 関数入口では、呼び出し側が積んだ引数がそのまま `slot 0..num_params-1` になる。
- `ret` を伴わずに本体末尾に達した関数は、暗黙に `void`（またはランタイム規約に応じて
  適切な既定）を戻す（§4.9 の `RET 0` 相当）。

| ニーモニック | オペランド | スタック効果 | 対応 AST | 説明 |
|---|---|---|---|---|
| `MAKE_CLOSURE` | `u16 chunk_idx` | `[ → fn]` | `EXPR_LAMBDA`/`STMT_FUNC` | チャンクから関数値を構築して積む |

### 4.9 関数呼び出し・複数戻り値・return（`EXPR_CALL` / `STMT_RETURN`）

**呼び出し規約**：

1. 呼び出し側は、まず被呼び出し関数値（`fn`）を push し、続いて引数を左から順に push する。
2. `CALL argc` を実行すると、VM はスタック上の `fn` と `argc` 個の引数を用いて新しい
   `CallFrame` を作り、`base` を「最初の引数の位置」に設定して被呼び出しチャンクへ移る。
3. 被呼び出し側は `RET n` で戻る。戻り値 `n` 個はスタック top 側に積まれている。VM は
   フレームを畳み、`base` 以降（引数・ローカル）を捨てて、戻り値 `n` 個を呼び出し側
   スタックへ残す。

| ニーモニック | オペランド | スタック効果 | 対応 AST | 説明 |
|---|---|---|---|---|
| `CALL` | `u8 argc` | `[fn a1..aN → r1..rM]` | `EXPR_CALL` | Myon 関数を呼ぶ。M は関数の戻り値個数 |
| `RET`  | `u8 n`   | `[r1..rn → ]`（フレーム破棄） | `STMT_RETURN` | 戻り値 n 個を残してフレームを畳む |

- **複数戻り値**（言語仕様 §6.2）：`ret x, y` は `x`, `y` を push してから `RET 2`。
  呼び出し側 `a, b = f()` は、`CALL` 後にスタックへ 2 値が残るので `STORE_LOCAL` を
  逆順に並べて受け取る。
- 呼び出し結果を 1 個だけ使う文脈で関数が複数値を返す場合は、余分な戻り値を `POP` で
  捨てるコードをコンパイラが生成する（言語仕様の代入規則に従う）。
- `error` を含む `(value, error)` 戻り（言語仕様 §6.2）は、単に「複数戻り値のうち末尾が
  error 型」として扱い、特別な命令は設けない。

### 4.10 配列・マップ（`EXPR_ARRAY_CTOR` / `EXPR_MAP_CTOR` / `EXPR_INDEX`）

| ニーモニック | オペランド | スタック効果 | 対応 AST | 説明 |
|---|---|---|---|---|
| `NEW_ARRAY` | `u16 type_idx` | `[ → arr]` | `EXPR_ARRAY_CTOR` | 空配列を作る。要素型は定数プールの `TypeSpec` を参照 |
| `NEW_MAP`   | `u16 type_idx` | `[ → map]` | `EXPR_MAP_CTOR` | 空マップを作る。K/V 型を参照 |
| `ARRAY_PUSH`| なし | `[arr v → arr]` | 配列リテラル初期化 | `array_push`。初期要素の充填に使用 |
| `INDEX_GET` | なし | `[c i → v]` | `EXPR_INDEX`（読み） | `c[i]`。範囲外は実行時エラー（§8） |
| `INDEX_SET` | なし | `[c i v → ]` | `STMT_ASSIGN`（`c[i]=v`） | 添字代入 |

- 配列・マップは実行時に構築するため、定数プールには入れない（§1.3）。要素の型情報
  （`TypeSpec`）だけは定数プールにシリアライズして持つ（§6.3）。
- マップのキー型は言語仕様（§14.2）に従い str/int を想定する。

### 4.11 構造体・メンバ・メソッド（`EXPR_MEMBER`、`self`、`myon.extends`）

| ニーモニック | オペランド | スタック効果 | 対応 AST | 説明 |
|---|---|---|---|---|
| `NEW_STRUCT` | `u16 type_idx` | `[f1..fN → st]` | 構造体コンストラクタ | フィールド値 N 個から構造体インスタンスを作る |
| `GET_FIELD`  | `u16 name_idx` | `[st → v]`  | `EXPR_MEMBER`（読み） | フィールド／継承フィールドを取得 |
| `SET_FIELD`  | `u16 name_idx` | `[st v → ]` | `STMT_ASSIGN`（`st.f=v`） | フィールドに格納 |
| `INVOKE`     | `u16 name_idx`, `u8 argc` | `[st a1..aN → r1..rM]` | `EXPR_MEMBER`+`EXPR_CALL` | メソッド呼び出し（`self`＝レシーバ） |

- 構造体コンストラクタ（言語仕様 §8）は、名前付き引数の順序をコンパイル時に宣言順へ
  並べ替えてから `NEW_STRUCT` に渡す。フィールド名の索引は定数プール（文字列）を使う。
- **`self`**：メソッドチャンクでは `self` を `slot 0`（第 1 引数相当）として扱う。`INVOKE`
  はレシーバ `st` を第 1 引数位置に置いてメソッドチャンクを呼ぶ。
- **継承（`myon.extends`）**：初期実装では **静的ディスパッチ**とする。メソッド解決は
  コンパイル時に「宣言に存在する最も近い定義」を決め、`INVOKE` の `name_idx` は解決済み
  メソッドを指す。動的ディスパッチ（実行時の型に基づく仮想呼び出し）が必要になった
  場合の拡張余地は §10 に記録する。フィールド名衝突の禁止（言語仕様 §14.6）は
  コンパイル時に検査する。

### 4.12 文字列補間（`EXPR_STRING` の `"... {expr} ..."`）

文字列補間は **コンパイル時に部分式へ分解**し、文字列結合命令列へ展開する。専用の
補間命令は設けない。

| ニーモニック | スタック効果 | 説明 |
|---|---|---|
| `STR_CONCAT` | `[a b → a++b]` | 2 つの str を連結して 1 つの str を積む |
| `TO_STR`     | `[v → s]` | 任意の値を str へ変換（`value_to_cstr` 相当）。`str()` と同じ |

```
# "Hi {name}, {age+1}"  のコード生成イメージ
    PUSH_CONST "Hi "        ; 定数
    LOAD_LOCAL name         ; {name}
    TO_STR
    STR_CONCAT
    PUSH_CONST ", "
    STR_CONCAT
    <age+1 を評価>
    TO_STR
    STR_CONCAT
```

- 補間を含む文字列リテラルは、コンパイラが「静的な文字列断片」と「`{}` 内の式」に
  分解し、上記のように `PUSH_CONST` / 式評価 / `TO_STR` / `STR_CONCAT` の列に落とす。
- 補間を **含まない**純粋な文字列は、そのまま 1 個の str 定数として定数プールに置く
  （§1.3）。

### 4.13 型キャスト・型チェック（`EXPR_STR_CTOR`/`EXPR_CHAR_CTOR`/`EXPR_INT_CTOR`/`EXPR_ERROR_CTOR`）

型コンストラクタ（言語仕様 §2.3）は変換も兼ねる。各コンストラクタに対応する命令を
設ける。

| ニーモニック | スタック効果 | 対応 AST | 説明 |
|---|---|---|---|
| `CAST_STR`   | `[v → s]` | `EXPR_STR_CTOR` | `str(v)`。`TO_STR` と同義だが AST 由来を明示 |
| `CAST_INT`   | `[v → i]` | `EXPR_INT_CTOR` | `int(v)`。`int("123")` 等。失敗は error/実行時エラー |
| `CAST_CHAR`  | `[v → c]` | `EXPR_CHAR_CTOR` | `char(v)`。1 文字制約を検査 |
| `MAKE_ERROR` | `[v → e]` | `EXPR_ERROR_CTOR` | `error(v)`。error 値を構築 |

- `int(...)` の変換失敗、整数オーバーフロー等は、ツリーウォーク版 Step12 と**同一の
  実行時エラー挙動**を再現する（§8）。

### 4.14 ネイティブ／モジュール呼び出し（標準ライブラリ）

`myon.print` / `myon.math.*` / `myon.string.*` / `myon.array` メソッド等の**組み込み関数**は、
命令として個別実装せず、**単一のネイティブ呼び出し命令**で C 側の関数テーブルを引く。

| ニーモニック | オペランド | スタック効果 | 説明 |
|---|---|---|---|
| `CALL_NATIVE` | `u16 native_id`, `u8 argc` | `[a1..aN → r1..rM]` | ネイティブ関数テーブル `native_id` を argc 引数で呼ぶ |

- `native_id` は、C 側で用意する **ネイティブ関数テーブル**（`{名前, 関数ポインタ,
  期待引数数, 戻り値数}` の配列）への索引。コンパイラは `myon.print` などの呼び出しを
  解決して `native_id` を埋め込む。
- ネイティブ関数のシグネチャは `Value fn(Value *args, int argc, Error *out)` のような
  統一形とし、既存の実装（`src/interpreter.c` 内の組み込み）を薄いアダプタで再利用する。
- **利点**：命令セットが肥大化しない。標準ライブラリ関数を追加してもテーブルにエントリを
  足すだけで済み、`.myc` フォーマットも命令セットも変わらない。

> **モジュール解決**：`module myon.stdio` 等（言語仕様 §11）の読み込みは、コンパイル時に
> 「どのネイティブ関数が利用可能か」を確定するためのものと位置付ける。`.myc` には
> 解決済みの `native_id` だけが残るため、実行時のモジュール探索は不要。

## 5. 静的スコープ解決アルゴリズム（コンパイル時）

ツリーウォーク版は実行時に `Env` の親チェーンを辿って変数を解決する。MVM では
**コンパイル時にスコープを解決してスロット番号を確定**し、実行時の探索コストを
排除する。これが本設計の高速化の中核である。

### 5.1 対象となる言語仕様

- ブロック（`{}`）スコープ（言語仕様 §9.1）。
- `myon.expose`：ブロック内変数を外側へ持ち出す（§9.1）。
- **シャドーイング禁止**（§9.2）：同名変数の再定義はエラー。
- 代入解決規則（§9.2 の 3 段階：現スコープ更新 → 外側更新 or ブロックならエラー →
  新規定義）。これは多重代入にも同様に適用。

### 5.2 データ構造：Scope と Local

コンパイラは、コンパイル中の各チャンクごとに「解決テーブル」を持つ。

```
Compiler(チャンクごと) {
    locals[]     : 宣言済みローカルの配列（宣言順 = スロット順）
        Local { name, depth, is_captured(将来用) }
    scope_depth  : 現在のブロックの深さ（関数本体= 0、{} に入るたび +1）
    next_slot    : 次に割り当てるスロット番号
}
```

- `locals[i].name` はソース上の変数名、`locals[i].depth` は宣言されたブロック深さ。
- スロット番号は `locals` 配列の添字にそのまま対応させる（`LOAD_LOCAL i` / `STORE_LOCAL i`）。

### 5.3 名前解決アルゴリズム

変数参照 `EXPR_IDENT`（読み）に出会ったとき：

```
resolve_local(name):
    for i from (locals.count - 1) downto 0:      # 後ろ（内側・新しい）から探す
        if locals[i].name == name:
            return i                              # スロット番号を返す
    # チャンク内に無い → main チャンクのグローバル、
    # またはネイティブ関数名、または未定義エラー（§5.6）
    return NOT_FOUND
```

代入 `STMT_ASSIGN`（`x = ...`）に出会ったとき、言語仕様 §9.2 の 3 段階規則を
コンパイル時に適用する：

```
resolve_assign(name):
    i = find_in_current_scope(name)              # depth == scope_depth のものだけ
    if i found:
        return (STORE existing, slot=i)          # (1) 現スコープの束縛を更新

    j = find_in_outer_scope(name)                # depth <  scope_depth
    if j found:
        if current scope is an explicit "{}" block:
            error "同名変数の再定義（シャドーイング禁止）"   # (2a) §9.2
        else:  # 関数本体などブロックでないスコープ
            return (STORE existing, slot=j)      # (2b) 外側を更新

    return (declare new local, slot=next_slot++) # (3) 新規定義
```

> **多重代入への適用**：`a, b = f()` は各ターゲット名について `resolve_assign` を
> 独立に適用する（言語仕様 §9.2 の通り、外側既存変数があればそれを更新）。

### 5.4 ブロックの出入りと `myon.expose`

- ブロック `{` に入るとき：`scope_depth += 1`。
- ブロック `}` を出るとき：`scope_depth` を戻し、そのブロック深さで宣言された
  ローカル（`depth == 抜けるブロックの深さ`）を `locals` から取り除く。実行時には、
  それらのスロットを `POP`（`value_free`）してスタックを縮める命令を出力する。
- **`myon.expose name`**（言語仕様 §9.1）：`name` のローカルの `depth` を **1 つ外側へ
  引き下げる**（＝ブロックを出ても破棄されないよう、生存範囲を外側スコープに繰り上げ
  る）。コンパイル時にスロットを外側の生存集合へ移し替えることで実現し、実行時に
  そのスロットの `POP` を出力しない。

### 5.5 `num_locals` の確定

コンパイル中に割り当てたスロットの最大数が、そのチャンクの `num_locals` になる。
これにより VM は関数入口でローカル領域を一括確保できる（§3.3）。

### 5.6 未定義変数・二重定義のコンパイル時検出

- 参照した名前がローカルにもグローバルにもネイティブにも無ければ、**コンパイル時
  エラー**「未定義の変数 `name`」を出す（`.myc` 生成を中止）。
- 同一スコープでの同名再定義は §9.2 に従いコンパイル時エラー。

これらを Step5 のコンパイラ段階で検出することで、`.myc` 実行時には名前解決に伴う
失敗が起きないことを保証する。

## 6. `.myc` ファイルフォーマット

`.myc` は MVM が直接実行するバイナリファイルである。全体は
**ヘッダ → 定数プール → チャンク表 → コード**の順に並べ、数値はすべて
**リトルエンディアン**で格納する。

### 6.1 全体レイアウト

```
+------------------+
| Header           |   固定長（§6.2）
+------------------+
| Source Info      |   元 .myon の検証情報（§6.5）
+------------------+
| Constant Pool    |   全チャンク共通の定数プール（§6.3）
+------------------+
| Native Table     |   参照するネイティブ関数名の一覧（§6.6）
+------------------+
| Chunk Table      |   チャンクのメタ情報＋コード（§6.4）
+------------------+
```

### 6.2 ヘッダ

| オフセット | 幅 | 内容 |
|---|---|---|
| 0 | 4 バイト | マジックナンバー `"MYC1"`（0x4D 0x59 0x43 0x31）。バージョン識別を兼ねる |
| 4 | 1 バイト | フォーマットバージョン major（初版 = 1） |
| 5 | 1 バイト | フォーマットバージョン minor（初版 = 0） |
| 6 | 1 バイト | エンディアン識別（1 = little）。将来 big を許すための予約 |
| 7 | 1 バイト | フラグ（予約、0） |
| 8 | 4 バイト | 定数プールのファイル内オフセット（`u32`） |
| 12| 4 バイト | 定数プールのサイズ（バイト、`u32`） |
| 16| 4 バイト | チャンク表のオフセット（`u32`） |
| 20| 4 バイト | チャンク数（`u32`） |
| 24| 4 バイト | エントリチャンク索引（通常 main = 0） |
| 28| 4 バイト | Source Info のオフセット（`u32`） |

- マジックナンバーの末尾数字 `1` はメジャーバージョンに一致させ、非互換な変更が
  入ったら `"MYC2"` のように更新する運用とする。
- 読み込み時にマジック不一致・エンディアン不一致・major 不一致であれば「この `.myc` は
  この MVM では実行できない」旨のエラーを出す（§8）。

### 6.3 定数プールのシリアライズ形式

定数プールはエントリの連続。各エントリは `[ tag(u8) ][ payload ]`。

| tag | 種別 | payload |
|---|---|---|
| `0x01` | int    | `s64`（8 バイト） |
| `0x02` | float  | IEEE754 `double`（8 バイト、LE） |
| `0x03` | str    | `u32 len` ＋ UTF-8 バイト列（NUL 終端は含めない） |
| `0x04` | bool   | `u8`（0/1）※通常は専用命令を使うため稀 |
| `0x05` | nil    | payload なし |
| `0x10` | typespec | `TypeSpec` のシリアライズ（§6.3.1） |

先頭に `u32 count`（エントリ数）を置き、続けて `count` 個のエントリを並べる。

#### 6.3.1 TypeSpec のシリアライズ

配列・マップの要素型など `TypeSpec`（`src/types.h`）を保存する必要がある。再帰構造を
前順で書き出す。

```
typespec := base(u8=Type) [ name(u32 len + bytes) ]      # STRUCT/TYPEPARAM のみ name
                          [ elem: typespec ]              # ARRAY/MAP の要素/値型
                          [ key:  typespec ]              # MAP のキー型
                          [ argc(u16) arg: typespec * ]   # ジェネリク引数（§7.4 が非対応なら 0）
```

- プリミティブ（int/float/str/char/bool/void/error/nil）は `base` のみで完結する。

### 6.4 チャンク表のシリアライズ形式

チャンク表は `u32 count`（＝ヘッダのチャンク数と一致）に続けて、各チャンクを並べる。

```
chunk :=
    name        : u32 len + UTF-8 bytes         # 診断用関数名
    num_params  : u16
    num_locals  : u16
    ret_count   : u16
    code_len    : u32
    code        : code_len バイトのバイトコード列
    line_len    : u32                           # (任意) 命令→行 対応表の要素数
    lines       : line_len × (u32 code_off, u32 line)   # 無ければ 0
```

- 命令列内の定数参照（`PUSH_CONST idx` 等）は §6.3 のグローバル定数プールを指す。
- チャンク間参照（`MAKE_CLOSURE chunk_idx`）はチャンク表の索引を指す。

### 6.5 Source Info（`.myon` との整合性検証）

`.myc` が、対応する `.myon` より **古くないか**を実行時に検証できるよう、以下を埋め込む。

| フィールド | 幅 | 内容 |
|---|---|---|
| `src_mtime` | `s64` | 元 `.myon` の最終更新時刻（Unix epoch 秒）。コンパイル時に記録 |
| `src_size`  | `u64` | 元 `.myon` のバイトサイズ |
| `src_hash`  | 32 バイト | 元 `.myon` 全体の SHA-256（またはより軽量な FNV-1a 64bit を先頭 8 バイトに） |
| `src_path`  | `u32 len` + bytes | 元 `.myon` の（記録時の）パス。相対解決の補助 |

**検証ロジック**（`./myon foo.myc` 実行時）：

1. 同じディレクトリに `foo.myon` が存在すれば、その現在の mtime／サイズ／ハッシュを
   `.myc` 内の値と比較する。
2. **不一致（`.myon` の方が新しい）** の場合は既定で**警告**を出す
   （「`foo.myc` は `foo.myon` より古い可能性があります。再コンパイルを推奨します」）。
   厳格モード（CLI フラグ、§9.2）では**エラー**にして実行を中止する。
3. `.myon` が存在しなければ（配布された `.myc` 単体実行）検証をスキップして実行する。

> ハッシュ方式（SHA-256 か FNV か）は Step5 実装時に確定してよい。ここでは「32 バイト
> 枠を確保し、実際に使うハッシュ種別をヘッダのフラグで示す」設計とする。

### 6.6 Native Table

`.myc` が参照するネイティブ関数（§4.14）の**名前**を並べた表。`CALL_NATIVE` の
`native_id` はこの表の索引を指す。実行時、VM は名前で C 側のネイティブ関数テーブルへ
束縛し直す。これにより、C 側のテーブル並び順が将来変わっても `.myc` の互換性が保たれる。

```
native_table := u16 count
                (u32 len + UTF-8 name) × count      # 例 "myon.print", "myon.math.sqrt"
```

## 7. 非対応機能（本スコープ外）

MVM 初期実装では以下を**非対応**とする。`.myc` へコンパイルしようとした時点で、
コンパイラが**明確なエラー**を出して停止する（ツリーウォーク版へ暗黙にフォールバック
させない。利用者の混乱を防ぐため）。

### 7.1 明示的に非対応とするもの

| 機能 | 対応 AST | エラーメッセージ例 |
|---|---|---|
| async / await | `myon.async` 関数, `EXPR_AWAIT` | 「MVM は async/await に未対応です。`.myon` として実行してください」 |
| ネットワーク | `myon.net` / `myon.http` | 「MVM は myon.net/myon.http に未対応です」 |
| C FFI | `module myon.ffi` | 「MVM は myon.ffi に未対応です」 |

これらは、まず「同期的な計算処理（制御構文・関数・配列・構造体・文字列・数値演算）」の
高速化を優先するという方針（`00_overview.md` / README ロードマップ）に沿うものである。
async/net/ffi の MVM 対応は将来の拡張課題として §10 に記録する。

### 7.2 エラー報告の要件

- 非対応構文を検出した位置（行番号）を、言語仕様 §6.2.1 の診断形式に合わせて示す。
- 「なぜ非対応か」「どう回避するか（`.myon` で実行）」を 1 行で添える。

### 7.3 クロージャ（ネスト関数の外側変数捕捉）

初期実装では、ネストした関数からの外側ローカル変数の捕捉（クロージャ）は**非対応**と
する。トップレベルのグローバルと関数引数・自ローカルのみを扱う。ラムダは自己完結
（外側変数を参照しない）ものに限る。捕捉が必要な場合は §10 の upvalue 拡張で対応する。

### 7.4 ジェネリクス（両論併記）

ジェネリクス（`myon.struct Box<T>` 等、言語仕様 §14.8/§15）の MVM 対応は、判断が
分かれるため **2 案を併記**する。最終判断は上流（プロジェクト側）に委ねる。

#### 案 A：コンパイル時の単相化（モノモーフィゼーション）

型引数の具体化ごとに、専用のチャンクを生成する（`Box<int>` と `Box<str>` を別チャンクに
展開）。

- **利点**：実行時に型引数を引き回す必要がなく、生成後のコードは非ジェネリックコードと
  同速。型の厳密性（言語仕様 §2.2）とも整合しやすい。
- **欠点**：使用された型の組合せぶんコードが増える（コードサイズ膨張）。再帰的ジェネリクス
  や型引数の網羅が難しく、コンパイラ実装が重い。全使用箇所を走査して具体化集合を
  求める解析が必要。

#### 案 B：非対応（初期スコープ外）

ジェネリクスを含むコードは §7.1 と同様に**明示エラー**で弾く。

- **利点**：Step5 コンパイラの実装が大幅に軽くなり、「まず動く MVM」に最短で到達できる。
- **欠点**：ジェネリクスを使うコードは高速パス（`.myc`）の恩恵を受けられない。

#### 本書の意見（判断材料）

**初期実装は案 B（非対応）を推奨する。** 理由は次の通り。

1. 本ステップの最優先事項は「同期計算処理の高速化を最短で出す」ことであり、単相化の
   解析コスト（全使用箇所の型具体化集合の算出）はスケジュールリスクが大きい。
2. 単相化は後方互換に配慮しやすい追加機能（新チャンクの生成のみで `.myc` フォーマットは
   §6 のまま）であり、MVM が安定してから **案 A を追加導入**しても設計上の破綻がない。
3. したがって「B で始め、A へ拡張する」という段階戦略が最も低リスク。案 A の実装は §10 に
   将来課題として残す。

> なお最終判断は上流で行う前提のため、コンパイラ側は「ジェネリクスに当たったら
> 明示エラー」を出す箇所を 1 か所に集約し、後で単相化パスへ差し替えられる構造に
> しておくことを Step5 へ申し送る。

## 8. 実行時エラーと整合性

MVM の実行時エラーは、ツリーウォーク版と**同じ意味論・同じ診断形式**（言語仕様
§6.2.1）を維持する。利用者から見て `.myon` と `.myc` の挙動差が出ないことが原則。

| エラー種別 | 発生命令 | 挙動 |
|---|---|---|
| 整数オーバーフロー | `ADD`/`SUB`/`MUL`/`NEG`/`CAST_INT` | 実行時エラー（言語仕様 §2.1） |
| ゼロ除算 | `DIV` | 実行時エラー |
| 型不一致 | 各算術・比較 | 実行時エラー（§2.2） |
| 範囲外アクセス | `INDEX_GET`/`INDEX_SET` | 実行時エラー |
| 変換失敗 | `CAST_INT`/`CAST_CHAR` | error 値 または 実行時エラー（言語仕様に準拠） |
| スタックオーバーフロー | `CALL` | 実行時エラー（§3.4） |
| 不正な `.myc` | ロード時 | ロードエラー（§6.2） |

- VM はエラー発生時、現在の `CallFrame` の `ip` から §1.4 の `lines[]` を引いて**ソース
  行番号**を復元し、言語仕様の形式で報告する。`lines[]` を持たない `.myc` では行番号を
  省略した簡易メッセージにフォールバックする。
- `(value, error)` 規約（言語仕様 §6.2）で回復可能なものは error 値として返し、回復
  不能なもの（オーバーフロー等、仕様が「実行時エラー」と定めるもの）は VM を停止する。

## 9. `.myon` と `.myc` の関係・CLI 設計案

> 実際のフラグ名・最終仕様は Step7（統合）で確定する。本節は**設計上の叩き台**である。

### 9.1 実行

| コマンド | 挙動 |
|---|---|
| `./myon foo.myon` | 従来通りツリーウォーク実行（**不変**） |
| `./myon foo.myc`  | MVM バイトコードとして実行（§6 のロード → VM 実行） |

- 拡張子（`.myon` / `.myc`）で実行パスを切り替える。加えて、ファイル先頭 4 バイトが
  マジック `"MYC1"` であれば拡張子に関わらず `.myc` として扱う（誤リネーム対策）。

### 9.2 コンパイル

```
./myon --compile foo.myon -o foo.myc     # foo.myon を MVM バイトコードへ
./myon --compile foo.myon                # 出力省略時は foo.myc を既定名で生成
```

補助フラグ（叩き台）：

| フラグ | 意味 |
|---|---|
| `--compile <src> [-o <out>]` | `.myon` → `.myc` コンパイル |
| `--dump-bytecode <file>` | `.myc`（または `.myon` をコンパイルした結果）を逆アセンブル表示（デバッグ用、`--tokens` に倣う） |
| `--strict-stale` | §6.5 の整合性検証で不一致を**エラー**にする（既定は警告） |
| `--run` | `--compile` と同時に指定でコンパイル後そのまま実行 |

- 既存の `--tokens` フラグ（`src/main.c`）と同じ流儀で、`main` の引数解析に分岐を足す
  形を想定する。**このステップでは `main.c` を変更しない**（Step7 で実装）。

## 10. Open Questions（将来の拡張課題）

本スコープ外だが、設計上意識しておくべき将来課題を記録する。

1. **値表現の刷新（方針 B）**：NaN-boxing またはタグ付きユニオンの平坦化で `Obj` の
   malloc/free と参照カウントを削減する。方針 A の `Value` と相互変換できる境界を
   設けておけば段階移行が可能。
2. **レジスタマシン化**：ホットな関数だけレジスタ割当した命令列に再コンパイルする
   ハイブリッド案。まずはスタックマシンで基盤を固めてから検討。
3. **ジェネリクスの単相化（§7.4 案 A）**：MVM が安定した後に追加導入。`.myc`
   フォーマット（§6）は変更不要な見込み。
4. **クロージャ（upvalue）**：`LOAD_UPVALUE`/`CLOSE_UPVALUE` とフレームの upvalue 表を
   追加してネスト関数の外側変数捕捉に対応する（§7.3）。
5. **async/await・net/http・ffi の MVM 対応**：協調的イベントループ（言語仕様 §14.9）を
   VM に統合する。当面は `.myon`（ツリーウォーク）側で実行する分業で十分。
6. **動的ディスパッチ（仮想メソッド）**：`myon.extends` の実行時型に基づく呼び出し。
   初期は静的ディスパッチ（§4.11）で開始。
7. **命令のスーパーインストラクション化**：`LOAD_LOCAL`+`LOAD_LOCAL`+`ADD` のような
   頻出列を 1 命令に融合してディスパッチ回数を減らす最適化。
8. **定数プールの型別分割**：int/float/str をプールごとに分けてキャッシュ効率を上げる案。

## 11. 実装優先順位（Step5/Step6 への申し送り）

Step5（AST→バイトコードコンパイラ）・Step6（VM 本体）が着手しやすいよう、段階的な
実装順を提案する。各段階で `tests/cases/` に `.myon`/`.out` の回帰テストを追加し、
`.myc` 実行結果がツリーウォーク版と一致することを確認しながら進めること。

| 段階 | 対象 | 命令 | 目標 |
|---|---|---|---|
| M0 | 最小 VM | `PUSH_CONST` `POP` `ADD`/`SUB`/`MUL`/`DIV` `PUSH_TRUE/FALSE/NIL` | リテラルと算術式だけが動く。`.myc` の読み書きと VM ループの骨格を作る |
| M1 | 比較・単項・論理 | `EQ`〜`GE` `NEG` `NOT` ＋ 短絡ジャンプ | 式の評価がひととおり完成 |
| M2 | 変数 | `LOAD_LOCAL` `STORE_LOCAL` ＋ §5 の静的スコープ解決 | 代入・参照・`myon.expose`・シャドーイング禁止の検証 |
| M3 | 制御構文 | `JUMP` `JUMP_IF_FALSE/TRUE` | if/elif/else, while, for, break/continue |
| M4 | 関数 | `MAKE_CLOSURE` `CALL` `RET` ＋ コールフレーム | 単一・複数戻り値、再帰、`(value, error)` |
| M5 | ネイティブ | `CALL_NATIVE` ＋ ネイティブ関数テーブル | `myon.print`/`myon.math`/`myon.string` 等が動く |
| M6 | 文字列補間・キャスト | `TO_STR` `STR_CONCAT` `CAST_*` `MAKE_ERROR` | 補間・型変換 |
| M7 | 配列・マップ | `NEW_ARRAY` `NEW_MAP` `ARRAY_PUSH` `INDEX_GET/SET` | コレクション |
| M8 | 構造体・メソッド | `NEW_STRUCT` `GET_FIELD` `SET_FIELD` `INVOKE` | struct・`self`・静的継承 |

**進め方の指針**：

- **M0→M1→M2 を最優先**で通す。ここまでで「バイトコード化の高速化効果」が計測可能に
  なり、以降の投資判断ができる。
- 各段階で、同じ `.myon` を「ツリーウォーク実行」と「`--compile` → `.myc` 実行」の両方で
  走らせ、出力（`.out`）・エラー（`.err`）が一致することを回帰テストで担保する
  （`00_overview.md` の共通ルールに従う）。
- 非対応機能（§7）に当たったら**明示エラー**を出す箇所を M0 の時点で 1 か所に用意し、
  段階が進むごとに対応済み機能をそこから外していく運用にすると、抜け漏れが防げる。

## 付録 B. Step5 実装ノート（設計との差分）

Step5（`src/mvm_compiler.c` / `src/mvm_chunk.c` / `src/mvm_bytecode.h`）でコンパイラ本体を
実装した際に、本仕様書の設計を具体化・微修正した点を記録する。VM 本体（Step6）はこの
ノートに従って `.myc` を解釈すること。

1. **オペコード番号の確定（§4.0）**：設計時に数値未確定だった各命令へ、§4.0 のバンド表に
   従って具体的な数値を割り当て、共通ヘッダ `src/mvm_bytecode.h`（設計案の `mvm_opcode.h`
   に相当）に `OpCode` enum として確定した。ファイル名は既存の 1 機能 1 ペア慣習に合わせ
   `mvm_bytecode.h` とした。

2. **`LOAD_GLOBAL` / `STORE_GLOBAL` の追加（§4.6）**：トップレベル変数はエントリ（`<main>`）
   チャンクのローカルスロットに置く（§4.6）が、ネストした関数からはフレーム相対の
   `LOAD_LOCAL` では届かない。再帰・相互再帰するトップレベル関数、関数内からのグローバル
   参照/代入のために、`<main>` フレームのスロットを直接指す `LOAD_GLOBAL(0x32)` /
   `STORE_GLOBAL(0x33)` を追加した。VM はエントリフレームのスロット配列を絶対参照すること。

3. **メソッドの `self` とチャンク名（§4.11）**：メソッドチャンクは `self` を `slot 0`
   （第 1 引数相当）に束縛し、宣言引数はその後ろ（`slot 1..`）に並べる。`num_params` は
   `self` を含めた個数（＝宣言引数数 + 1）とする。可読性と Step6 の静的ディスパッチ用
   メソッド表構築のため、メソッドチャンク名は `"Struct.method"` 形式で登録する。

4. **構造体コンストラクタと継承フィールド（§4.11 / 言語仕様 §14）**：`NEW_STRUCT` に積む
   フィールド値の順序は、ツリーウォーク版 `collect_fields()` と同一の「継承チェーンを親
   優先で平坦化した順」に統一した。名前付き引数はフィールド名で束縛し、名前なし引数は
   同順位のフィールドへ束縛する。`NEW_STRUCT` のオペランドは構造体名の定数プール文字列
   索引（`u16`）で、VM は名前から構造体定義を引いてフィールド順を復元する。

5. **`for ... in` の脱糖（§4.7）**：range 形式は隠しカウンタ＋`LT`＋後方 `JUMP` に、
   iterable 形式は隠しインデックス `i` と `myon.len` ネイティブ呼び出しによる範囲判定＋
   `INDEX_GET` に脱糖する。隠しローカルは名前先頭に空白を付けてユーザ名と衝突しないように
   している。

6. **`.myc` フォーマットの補足（§6）**：ヘッダ magic は `"MYC1"`、多バイト値はすべて
   リトルエンディアン。ネイティブ関数テーブル（§6.6）は定数プールの直後に配置する。
   Source Info（§6.5）のハッシュ欄先頭 8 バイトにソースの FNV-1a 64bit を格納する
   （残り 24 バイトは 0 埋め。将来 SHA-256 等へ拡張可能）。

7. **検証手段（Step5 検証方法）**：`./myon --dump-bytecode <src|.myc>` で逆アセンブルを、
   `./myon --compile <src> [-o out.myc]` で `.myc` 出力を行う（CLI フラグ名は Step7 で最終
   決定する暫定仕様）。`tests/mvm_compiler_tests.sh` が「全 `tests/cases/*.myon` が
   クラッシュしないこと」「非対応機能が §7 のエラーになること」「`tests/mvm_dump_samples/`
   の `.myc` ラウンドトリップが安定なこと」を機械的に検査する。

未実装で Step6 へ持ち越した項目：`ARRAY_PUSH`（配列リテラルの初期要素充填。現状の言語には
配列リテラル構文がなく `myon.array(T)` の空配列生成のみのため未使用）、および動的
ディスパッチ（§10）。
